    Priority and Preemption

    This page covers three features of a resource. Task priority ranks the waiting requests: a lower priority value is served first. Preemption lets a request take a unit from a task whose priority value is higher than its own. A breakdown takes every unit away until a repair.

    How to Use It

    Task Priority

    Under queue: priority, each task gives its requests a priority. The priority can be a number, the same for every run of the task. It can be an expression, read when the task joins the queue, such as attr.tier for the entity's attribute tier. In the builder, it can also be a function of the task id and the entity's attributes. The attributes exist before the request queues, but the task's own payload does not, so a priority cannot read that payload. An expression can read the previous task's payload as payload.<field>. A lower priority value is served first, and a task with no priority ranks 0, as a SimPy PriorityRequest does. Equal priorities are served first in, first out, as in SimPy's PriorityResource. SimPy ranks a request by (priority, time, not preempt), so among requests with equal priorities and times, a request that may preempt goes before one with preempt: false. The tests check it, ties included, in all three APIs (SimPy Compatibility).

@app.task(
    service_id="packing",

    return {"event_type": "order_packed"}

    A low-level process passes the priority to the request: packers.request(priority=entity.attributes["tier"]), as the queue-order example above does. A request with no priority has priority 0. A resource whose queue is fifo or lifo ignores it.

    A priority on a task whose resource does not have queue: priority is refused when the blueprint loads, or when run() starts. Priorities shows what priority does to waits.

    Preemption

    On a resource with preempt: true, which needs queue: priority, a request that finds every unit busy takes a unit from a task with a higher priority value, as SimPy's PreemptiveResource does. SimPy's rule chooses the task that loses the unit. It sorts the users by (priority, request time, may not preempt) and picks the one that sorts last, but only when that user sorts after the new request. A user with an equal priority made its request earlier, so it sorts before the new request, and equal priorities do not preempt. The one exception is a user whose request was made at the same moment as the new one, with preempt: false: it sorts after a request that may preempt. The task that loses the unit publishes preempted with the resource's name, the key of the entity that took the unit (preempted_by) and the time the task was granted the unit (usage_since). It then follows its on_interrupt, as it would for an interrupt (Interruptions). A task with preempt: false never takes a unit this way. The interruptions example lets express orders preempt regular ones:

    def pack(env, sampler, shop, key, priority, task_id):
    """Packs one order; a preemption or an interrupt sends it back to the queue
    with the packing time it had left."""
    path_id = "Shop.service.packing"

    def publish(value):
        env.publish_event(key, value, task="pack", instance=task_id)

    env.stats.flow_started(key.rsplit("-", 1)[0])  # the order enters the shop
    publish({"path_id": path_id, "status": "queued"})
    env.stats.task_queued("pack", task_id)
    remaining, started = None, False
    shop["packing"].append(env.active_process)
    shop["keys"][env.active_process] = key
    while True:
        request = shop["packers"].request(priority=priority)
        since = None
        try:
            yield request
            if not started:
                started = True
                publish({"path_id": path_id, "status": "started"})
                env.stats.task_started("pack", task_id)
            else:
                publish({"path_id": path_id, "status": "resumed"})
                env.stats.task_resumed("pack", task_id)
            if remaining is None:
                remaining = sampler.sample(env.registry.get_config(path_id))
            since = env.now
            yield env.timeout(remaining)
            payload = {"event_type": "order_packed", "priority": priority}
            publish(payload)
            env.stats.task_finished("pack", task_id)
            shop["packers"].release(request)
            break
        except simpy.Interrupt as interrupt:
            request.cancel()
            shop["packers"].release(request)  # nothing to give back if preempted
            if since is not None:
                remaining -= env.now - since
            if isinstance(interrupt.cause, Preempted):
                value = {
                    "path_id": path_id,
                    "status": "preempted",
                    "resource": "packers",
                    "preempted_by": shop["keys"].get(interrupt.cause.by),
                    "usage_since": interrupt.cause.usage_since,
                }
                publish(value)
                env.stats.task_interrupted("pack", task_id, preempted=True)
            else:
                value = {"path_id": path_id, "status": "interrupted"}
                publish({**value, "cause": interrupt.cause})
                env.stats.task_interrupted("pack", task_id)
    shop["packing"].remove(env.active_process)
    del shop["keys"][env.active_process]
    env.stats.flow_finished(key.rsplit("-", 1)[0])

    DynamicResource(env, "Shop", "packers", queue="priority", preempt=True) builds the resource, and request(priority, preempt=True) asks for a unit. The process that loses its unit receives simpy.Interrupt with a SimPy Preempted cause, whose resource, by (the process that took the unit) and usage_since say what happened.

    A gift order with preempt: false is served before any regular order that waits. But it waits for the packer to be free, rather than take it from a regular order being packed:

    Breakdowns

    A breakdown makes a resource fail at random and be repaired. time_to_failure is the time from the start, or from a repair, to the next failure. It counts all simulation time, busy or idle. repair is how long a repair takes. While the resource is down its effective capacity is 0 and no request is granted:

    Start run_breakdowns(env, station, sampler, work="interrupt") as a SimPy process beside the arrivals. station.fail() and station.repair() put a resource down and back by hand.

    work says what happens to the tasks being served. Under interrupt, the default, each task is interrupted with the cause breakdown and follows its on_interrupt. Under finish, the tasks finish their work. Each failure and repair publishes an event keyed by the resource's name, with status down or repaired and reason: failure. Model Breakdowns checks the downtime of the example, and Interruptions explains on_interrupt.

    Example: Interruptions

    In the interruptions example, express orders preempt regular ones, and a fire drill at 60 seconds interrupts the order being packed. Each interrupted order resumes with the packing time it had left. It needs no Docker service and ends on its own after 120 simulation seconds.

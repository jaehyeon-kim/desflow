    What Is Discrete-Event Simulation?

    If you have never used simulation, start here. No maths is needed: a simulation is a way of playing out "what would happen if" on a computer, one step at a time, instead of guessing from averages.

    Simulation in Everyday Terms

    Think of a packing shop. Orders arrive about every 2 seconds, and a packer takes 1.5 seconds to pack one. Will orders queue in the busy hour? What if a second packer starts at 9:30, or a delivery brings twenty orders at once?

    You could answer by watching the shop with a notebook. You would not write something down every second, because most seconds nothing changes. You would write only the moments when something happens: an order arrives, a packer starts on it, the order is packed. Each of those moments is an event, and the notebook is enough to tell you who waited and for how long.

    The diagram shows the shop and the notebook. The shop is orders, a queue and packers. The notebook lists only the moments when something changes.

    A discrete-event simulation (DES) is that notebook, written by a computer. You describe the shop: how often orders come, how long packing takes, how many packers there are. The computer then plays out the events one after another, with random variation like in real life, and writes down what happens. Because it skips the quiet seconds, it can play out a day, or a year, in moments. Change the description, add a packer or double the orders, and run it again to see the difference.

    desflow does this for any system with arrivals, work and limited capacity: a factory, a warehouse, a shop, a support desk, a network. What it adds is that every event is also sent out as a record, to Kafka, a database or files, so the simulation becomes a source of realistic data. Building Blocks shows the parts you describe a model with, and Queues and Capacity explains why a queue grows the way it does.

    Running a model is one step of a study. The question comes first, and the checking and the analysis of the runs come after. A Simulation Study walks through all of it.

    Events and the Event List

    This section is the same idea in the terms the rest of the docs use. The terms follow two sources. One is chapter 3, General Principles, of Banks, Carson, Nelson and Nicol, Discrete-Event System Simulation, read through lecture notes on that chapter. The other is Ingalls, "Introduction to Simulation" (Winter Simulation Conference, 2001), read through its published text. The explanations are our own.

    A discrete-event simulation models a system as a series of events: an order arrives, a packer starts on it, the packer finishes. Each event happens at an instant, and between two events nothing changes. The simulation therefore only needs to visit the instants when events happen. It keeps a list of the events to come, in time order. It takes the earliest, moves its clock straight to that instant, and carries the event out. Carrying out an event usually schedules more: when a packer starts on an order, the simulation schedules the end of packing 1.5 seconds later.

    The clock jumps from one event to the next. A simulated week with a few thousand events therefore takes only the time needed to compute those events, not a week. desflow runs on SimPy, which provides the event list and the clock. On top of SimPy it adds:

    • Pacing. factor makes the clock follow the wall clock (1.0), run faster or slower, or not wait at all (0.0), so the same model can drive a live dashboard or write a month of history in seconds. Time and Pacing explains it.
    • Live values. Every parameter is in a registry and can change while the simulation runs. Live Parameters explains it.
    • Records. What happens is published as events and telemetry to the sinks you attach. Records and Telemetry shows the formats.

    Two events can fall at the same instant. They run by priority and then in the order they were scheduled. Run Length shows the detail.

    Entities, Resources and Queues

    The things that flow through a model are entities: orders, visitors, support calls. An entity arrives, needs something that is limited, such as a packer or a packing bench, holds it while it is served, and leaves. That limited thing is a resource. When every unit of a resource is busy, the next entity waits in its queue. Arrivals, service times, resources and queues are what a model is built from. Building Blocks covers each one.

    An entity can carry attributes: facts about it that stay with it as it moves, such as an order's priority or the area its items come from. A rule can read them to decide which task comes next or which order a packer takes first. Task Flow shows how, and A Flow of Tasks sets them as an order moves from step to step.

    The time an entity spends in a model is of two kinds. An activity is a period of set length, such as the 1.5 seconds of packing. A delay is time spent waiting for something, such as a free packer, and its length is not set by the model: it comes out of the state of the system. You describe the activities, and the simulation produces the delays. The wait in the queue is a delay, which is why it is a result and not an input. Arrivals and Services shows how to set an activity's length.

    Queues are where the interesting behaviour comes from. Two models with the same average times can have very different waits, because a run of quick arrivals or one slow job holds everyone up. A simulation shows that directly, where an average cannot. Queueing Basics explains the results of queueing theory that a model can be checked against.

    From Model to Records

    A model on its own only moves its clock. What makes it useful here is what it publishes. A task publishes queued, started and a finished event for every entity, and telemetry reports what you choose, such as how many units of a resource are busy. A sink writes each record to Kafka, a database or files, so the simulation becomes a source of realistic data for whatever reads it.

    Whether that data looks real depends on the model being stable: if work arrives faster than the resources can finish it, the queue grows without limit and every later event is delayed more. Queues and Capacity explains how to tell, and how to fix it.

    How long to run depends on the question. Banks et al.'s lecture notes on output analysis separate two kinds of study:

    • A terminating run has a natural end: the shop opens empty and closes at the end of the day, and the day's results are the answer.
    • A steady-state study asks how the shop behaves in the long run, after the effect of its empty start has gone, so the start of each run is left out as a warm-up.

    The same model can be run either way, depending on the question. Output Analysis explains both, and Run Length shows how to set the end of a run.

    Command Line

    The desflow command runs a model without a line of Python, and also checks it, compares designs, fits measured times and converts a distribution's parameters. This page uses each command in the order a study uses it, on one shop, and says what each output tells you.

    What It Is

    desflow is installed with the package: uv tool install desflow, or pip install desflow. Each task is a command of its own, such as desflow run or desflow explain. desflow on its own lists them by task, with examples. The --help of each command, such as desflow run --help, lists its options and ends with examples of that command. Each command below links to a page with its full help:

    Command What it does
    desflow run Build the simulation in FILE and run it, or run replications of it.
    desflow check Check that each blueprint or builder file in FILE... builds, without running it.
    desflow test Run the tests of each file in FILE... and report the statistics that differ.
    desflow explain Show the model in SOURCE as a graph, with its utilisation, status, waits and tuning hints where the queueing formulas apply, and why where they do not.
    desflow experiment Run the experiment in FILE and write its artifacts and report.
    desflow report Build the report of an experiment again from the artifacts in FOLDER.
    desflow fit Fit a column of FILE to the distribution families, and exit 1 if none is usable.
    desflow dist List the distribution families, or convert parameters to a mean and std and back.
    desflow schema Print the blueprint JSON Schema.
    desflow examples List the examples, or download one at the version you have installed.
    desflow examples list List the examples, with what each shows and what it needs.
    desflow examples get Download an example into <dest>/<name>/<api>/, at the installed release.

    Usage: desflow [OPTIONS] COMMAND [ARGS]...

  Run, explain and analyse desflow simulations, fit their inputs, and download
  the examples.

Options:
  --version  Print the installed version and exit.
  --help     Show this message and exit.

Commands:
  run         Build the simulation in FILE and run it, or run replications...
  check       Check that each blueprint or builder file in FILE...
  test        Run the tests of each file in FILE...
  explain     Show the model in SOURCE as a graph, with its utilisation,...
  experiment  Run the experiment in FILE and write its artifacts and report.
  report      Build the report of an experiment again from the artifacts in...

  Examples:

    # Run a blueprint, sending its records to its sinks

    $ desflow run shop.yaml

    # Print the first five events, with no services

    $ desflow run shop.yaml --sample 5

    # Find the bottleneck before running

    $ desflow explain shop.yaml

    # List the examples, then download one

    $ desflow examples list

    $ desflow examples get local

    The shop on this page is the model of the experiment example: two packers, an order every 2.5 seconds on average, and 4 seconds of packing on average. Every command runs in one folder and needs no Docker service. desflow fit needs the fit extra: uv tool install "desflow[fit]", or pip install "desflow[fit]".

    How to Use It

    Get an Example

    Check a File Before You Run It

    desflow check builds each blueprint or builder file you give it, and does not run it. It reports what desflow run reports before the clock starts: YAML errors, unknown keys, missing names, unset variables, !python references that cannot be imported, and connectors whose extra is missing or whose settings are refused. It does not call run.before, contact a broker, a database or a catalog, or run a !python function. Importing a !python module runs its top-level code, as desflow run does. It prints ok FILE (sim_id ID) for each valid file and every error of an invalid one, and exits 1 if any file is invalid.

    The commands below use a small shop in a file of its own. Its packers come from the variable PACKERS, 2 when it is not set, and it holds one test. Save it as shop.yaml:

    # A small shop for the commands of the Command Line page that need a file with a
# variable and a test. The packers come from PACKERS, 2 when it is not set.
# Run it with: desflow run shop.yaml --sample 5
simulation: {sim_id: Shop, factor: 0, random_seed: 42}

resources:
  packers: {current_cap: "${PACKERS:-2}", max_cap: 5}

services:
  packing: {dist: gamma, shape: 4, scale: 1 s}

arrivals:
  orders: {dist: exponential, rate: 0.4, spawn: pack}

tasks:
  pack:
    service: packing
    resource: packers
    payload: {event_type: order_packed}

stats: basic

run: {until: 10 min}

# desflow test runs the model once at the seed and compares these statistics
tests:
  - name: two packers
    expect:
      tasks.pack.finished: 254
      tasks.pack.wait_mean: {value: 4.592, within: 0.001}

    A builder file has no ${PACKERS} variable and no test section: its values are Python. desflow check and desflow run take a builder file too, and Test a Model shows how to test one with pytest.

    A low-level script is not a file the command reads. Run it with python, and test it with pytest as Test a Model shows.

    desflow check takes more than one file, and --var NAME=VALUE fills ${NAME} in the files and in the files they include, before the environment does. Repeat --var for more variables:

    1
2
    desflow check shop.yaml
desflow check shop.yaml experiment/yaml/experiment_shop.yaml --var PACKERS=3

    It also warns about a run with no end: an arrival with a dist or a gap and no max_events, in a file with no run.until, run.stop or run.segments. The experiment's shop gives no until, because the experiment file gives it, so check warns about it and still prints ok. A tests entry with no seed, in a file with no seed of its own, is reported as desflow test reports it.

    desflow ships no pre-commit hook. A repository that keeps its blueprints in a folder can add its own to .pre-commit-config.yaml. pre-commit passes the changed files as the arguments, which check takes:

    .pre-commit-config.yaml
    1
2
3
4

    repos:
  - repo: local
    hooks:
      - id: desflow-check
        name: desflow check
        entry: desflow check
        language: system
        files: ^models/.*\.ya?ml$

    desflow test runs the tests that a file holds under tests. A test names a seed, an end time and the statistics its run must give. It runs the model once, unpaced, with no ingress and no egress, so a test contacts no service. It prints ok for each passing test and each difference of a failing one, and exits 1 if any test fails. A file with no tests prints no tests. A builder file reads its tests from a tests.yaml in its folder. --fix writes the measured statistics into the values that differ, and into a test with none, in place of reporting the differences. Read the changes before you keep them, because a test states its numbers at one seed of one desflow version. Test a Model writes tests step by step.

    1
2
    desflow test shop.yaml
desflow test shop.yaml --fix --var PACKERS=2

    Check It Before a Long Run

    desflow explain reads the model without running it. It draws the model as a graph and works out each resource's utilisation, the share of its units that the arrivals keep busy. SOURCE is a blueprint, a builder Python file with a module-level SimulationContext, or a URI such as s3://bucket/sims/shop.yaml. A URI that ends in a folder is refused with its name, such as Error: no file s3://bucket/models/.

    1
    desflow explain experiment/yaml/experiment_shop.yaml

    The packers are at utilisation 0.8: they are busy 80% of the time. An order arrives every 2.5 seconds on average (24 a minute, rate 0.4/s in the graph). Each order needs 4 seconds of a packer, and 2 packers share the work. The resources table names its columns with the usual queueing symbols:

    • λ (lambda) is the arrival rate, 0.4 orders a second.
    • μ (mu) is the rate one packer serves, 0.25 orders a second (4 seconds each).
    • ρ (rho) is the utilisation.
    • Wq is the mean wait in the queue, and L the mean number of orders in the shop. Both show - when no formula applies.

    The line Bottleneck: packers names the resource with the highest utilisation. Relieving it makes the next busiest resource the bottleneck. The status is OK below 0.85, CONGESTED from 0.85 and UNSTABLE from 1, where the queue grows for as long as the run lasts. The table by units shows that one packer would be UNSTABLE. The hints give the units and the arrival rate that reach the target of 0.85. A hint of more units than the resource's max_cap also says to raise max_cap, because a current_cap above max_cap is lowered to it.

    To keep a resource stable, lower its utilisation or its variability: more units (a higher current_cap), a shorter service time, a lower arrival rate, or less variable gaps or service times. To test how a consumer of the records copes, do the opposite on purpose. From utilisation 0.85 a resource is congested, with long waits that come and go. Above 1 it is overloaded and its queue grows for as long as the overload lasts.

    --target sets the utilisation the hints aim for, 0.85 by default. At 1 or above the hints are for deliberate overload. This command uses the shop of Queues and Capacity, saved as queues_and_capacity.yaml:

    1
    desflow explain queues_and_capacity.yaml --target 1.2

    The end of the output is the hints:

    With 2 packers the shop runs at utilisation 1.35, above the target of 1.2. With 1 packer, an arrival rate of 0.8 orders a second (an order every 1.25 seconds, 48 a minute) gives exactly 1.2.

    Run It

    Each order publishes queued when it joins the packers' queue and started when a packer takes it. The first two orders find a packer free, so each starts at the moment it queues. Without --sample, desflow run runs the model with its own settings and sinks. A model that runs out of events before the sample is full ends with exit 0 and the records it made.

    --var NAME=VALUE fills ${NAME} in the file and in the files it includes, before the environment does, and check and test take it too. explain and experiment do not take --var. --watch runs the file in a child process and runs it again whenever the file, or a .py file beside it, changes, so a change to a blueprint shows its first events at once. It needs the watch extra: pip install "desflow[watch]". Press Ctrl+C to stop it:

    1
2
    desflow run shop.yaml --var PACKERS=3 --sample 5
desflow run shop.yaml --sample 5 --watch

    --stdout prints the run's records as JSON lines, instead of writing to the file's sinks.     How It Works

    Each command reads its file and calls the library function a Python script would call. desflow run loads the model with load_context and runs it once, or calls replicate when --replications is given. desflow experiment calls run_experiment, desflow report calls write_report, and desflow fit reads the column and calls fit_column. desflow dist, desflow schema and desflow examples read the distribution table, the blueprint schema and the list of examples. A command therefore gives the same result as the Python call with the same arguments.

    desflow explain takes the most steps. Look at them in order:

    Graph. explain builds the graph from what the model declares: its arrivals, tasks, resources, stores, containers and next shares. It builds and runs nothing. Code the model does not declare, such as a hand-written arrival loop or an add_process function, becomes an opaque node. The graph also has an edge with no share from a task to each task it starts by an on: or listen spawn, a task branch of wait, open or subscribe, a spawn in the on: of a signal it fires, and on_interrupt_next and on_interrupt_run. next weights, fixed or computed, end no flow.

    Rates. Each task's arrival rate comes from flow balance: the rate from its arrivals plus the share of each task that sends work to it. A next function or a hand-written arrival loop makes the rates unknown, because the graph cannot see where the work goes. A task reached by an edge with no share has no rate either, with the reason "how often starts it is not known before a run" or "the split after depends on the run".

    Coverage. The formulas hold for a plain network of queues:

    • Each task holds at most one resource.
    • Each queue serves in arrival order, fifo or lifo, which give the same mean wait.
    • Nothing blocks, removes, delays or reorders work by priority.

    Anything else marks tasks, and the rate of a marked task is unknown. These mark tasks:

    • A task feature, such as put, patience, fail, a service_time (computed service time) or an interrupt that names the task (interruptions (an interrupt names it)), marks that task and every task after it.
    • An arrival feature gives the arrival no rate, so the tasks it starts have none: a gap (computed gaps), a count, keys, a key that can repeat or max_events (limited or repeated arrivals), a group other than 1, and active: false. A spawn count other than 1 is a feature too.
    • A resource feature, such as queue_limit, breakdowns, a capacity that an on: entry sets, a resource family, or a resource picked by key or lowest, marks the tasks that use it and every task after them.
    • A router with a weight that is an expression ends no flow and has no shares.
    • A priority queue whose tasks have different priorities marks every task after its tasks. The resource keeps its utilisation but has no wait.
    • An unstable resource marks every task after its tasks. The resource keeps its status.
    • A scenario step, live ingress or an add_process function marks every arrival and every task.

    A resource used by a marked task has no supported utilisation, status or wait, and the output names the reason under Not estimated.

    Waits. The utilisation ρ is λ ÷ (c × μ): the arrival rate divided by the units times the rate one unit serves. The status follows from it. The wait depends on the units and the input:

    • With no unit limit, the wait is 0.
    • At one unit, the wait comes from Kingman's formula. It is exact when the input is Poisson, and an approximation when one arrival with other gaps feeds the resource's only task.
    • At more than one unit, the wait comes from Erlang C, which needs Poisson arrivals and one exponential service time shared by every task that uses the resource.
    • With any other input or times there is no wait, and the output says to run --verify.

    Little's law then gives the queue length and the number in the system. The bottleneck is the resource with the highest supported utilisation. The hints solve the utilisation alone for the units and the arrival rate that reach --target.

    Verify. --verify runs the model as one replication does: unpaced, with no ingress or egress, and with the typical statistics. It measures from the end of the warm-up to --until, or to the blueprint's run.until when --until is not given. It compares four measures with the analysis: each resource's utilisation and queue length, the wait of each task that holds one resource, and each arrival's throughput. A measure agrees with the analysis:

    • For one run, when it is within 10% of the analysis, or measures 0 where the analysis gives 0.
    • For replications, when it is within the 95% interval's half-width or 1%, whichever is larger.

    A measure is not compared in these cases:

    • The analysis has no value for it.
    • Its resource is unstable.
    • Its wait comes from Kingman's formula as an approximation.
    • For a throughput, the arrival starts no task the graph shows, or its flow passes a marked task or an unstable resource.

    Stability and Limits

    • Inputs are files. run reads a blueprint, or a builder file with --sample (not with --stdout, --var or --watch), check a blueprint or a builder file, test a blueprint or a builder file with a tests.yaml, explain a blueprint or a builder file with a module-level SimulationContext, experiment an experiment file, and fit a CSV file. For a Python model, use replicate and run_experiment, as Replications shows.
    • Examples need the network. examples get downloads from GitHub at the installed release's tag. --ref picks another tag or branch.
    • explain --json is experimental. Its shape can change in 1.x, and schema_version changes with it.
    • Exit statuses: 0 on success, 1 on a failure, 2 on a usage error.
      • 1: run, check, test or explain cannot load the file, a test differs from the measured statistics, an experiment check fails (its files are still written), fit finds no usable family, or dist has no formula from a mean and a standard deviation for the family.
      • 2: a missing file, an option value that is not valid such as --until abc, a value that is not a number in a fit column, or an experiment file that is not valid.

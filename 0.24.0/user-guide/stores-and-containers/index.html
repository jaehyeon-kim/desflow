    Stores and Containers: DynamicStore and DynamicContainer

    A resource is held and given back. Stores and containers hold things that tasks take away and add: items, or an amount. This page shows how to declare them, how tasks put and get, and what a live change does.

    What It Is

    • A store holds items, each one a value of its own: parcels on a shelf waiting for a courier, orders in a buffer. A task puts an item in, and another takes the oldest out.
    • A container holds an amount: boxes in a bin, fuel in a tank, a stock level. A task takes some, and another adds some.

    Both have a capacity, or no limit. A task that takes waits while there is not enough, and a task that adds waits while there is no room. Stock uses a container in the shop.

    How to Use It

    Declare Them

    A container has a current_cap, its capacity, the largest amount it holds; a max_cap, the largest capacity a live change can set; and a level, the amount it holds when the run starts, 0 when left out. A store has a current_cap and a max_cap, in whole items, and starts empty unless it lists items (Start With Items and Serve by Priority). run() builds a DynamicContainer and a DynamicStore for each one the context declares; a store and a container cannot share a name.

    A DynamicContainer built with no init starts at the level its ContainerConfig gives; init= sets another.

    A store or container with no current_cap has no capacity limit, as simpy.Store(env) and simpy.Container(env) have: a put never waits for room. current_cap: .inf in YAML, or float("inf") in code, says the same. A max_cap alone gives the current_cap, and a current_cap alone gives the max_cap. A live update can give a store with no limit a number, which a store holds as a whole number of items and rounds down when it is a fraction, and .inf or the text "inf" sets no limit again. A store or container with no limit publishes capacity as null.

    Take and Add

    A task takes with get and adds with put. For a container, each names the container and an amount: a number; an expression, such as payload.boxes for a field of the previous task's payload; or in the builder, a function of the task id and the previous task's payload. The amount is 1 when left out. For a store, each names the store: a put adds the task's finished payload as the item, and a get takes the oldest item and passes it to the task's function as item.

    get(amount), put(amount), put(item) and get() are SimPy events: yielding one waits until it succeeds, and a store's get() succeeds with the item.

    A task with a resource gets its unit first and then takes its get, so it waits for stock while holding the unit. A task adds its put after its service time, then publishes the finished event. Tasks and Processes lists every step.

    A put or get makes the task wait until it is granted. With wait: false ("wait": False in the builder) the task makes the request and goes on at once, as a SimPy put that is not yielded: it publishes finished without waiting, and the request stays in the queue until it can be granted. Requests that are not waited for are granted first in first out with the others. An interrupt, on_interrupt: abandon and patience never cancel one, and a run ends without a request that is still waiting. A drain does not wait for it. A get with wait: false takes its item later and drops it, so it cannot use item_field or a function that declares item, and item.<field> can be read only in its own filter. wait: false is refused in a branch of a wait. The pump task of Example: Fuel Dock puts fuel into a tank this way; the third pump finds only 20 of room and its put stays queued.

    Start With Items and Serve by Priority

    A store can hold items when the run starts, as parcels left from yesterday: items lists them in the order a get returns them. A store with priority returns the item with the lowest priority first, as SimPy's PriorityStore does; its items are [priority, item] pairs, and a task's put gives each new item its priority: a number, an expression such as attr.priority, or any other value that can be ordered against the others, such as a list [1, 2], which orders element by element as a tuple does. In YAML a string is an expression, so a text priority such as 'P1' comes from attr.grade or payload.grade. A priority keeps the value it is given, so the text '10' sorts as text, before '9'. Priorities that cannot be compared, such as a number and a text, raise TypeError at the put, as in SimPy. Items of equal priority come out in the order they went in. A store cannot start with more items than its current_cap; the blueprint or add_store is refused with the reason.

def courier_process(env):
    first = yield parcels.get()  # a PriorityItem; .item is the parcel
    print(f"collected {first.item['order']}")
    # A put of your own wraps the item the same way, so ties keep their order
    yield parcels.put(parcels.wrap({"order": "express-1"}, 1))

    A low-level priority store holds simpy.PriorityItems. wrap(item, priority) makes one ranked by the priority and then by a rising number, which is how the builder and YAML keep equal priorities in order; a plain PriorityItem(priority, item) also works, with no order among equal priorities.

    A get on a priority store takes no priority of its own and is refused with one: the item's priority decides the order. Priorities compares priority storage with a resource's priority queue.

    Pick an Item, or Give Up Waiting

    A store get can take a filter, a condition that picks which item it takes, as SimPy's FilterStore does. item.<field> reads the item offered, beside the names any condition reads, such as attr.area for the entity's own attribute. The get takes the oldest item that matches and waits while none does; a waiting get that matches nothing does not stop a later one from taking an item that matches it. A priority store takes no filter, because SimPy has no store that both ranks and filters; the blueprint or run() refuses one with the task's name.

    A task's patience covers its whole wait, for its wait, then its resource and then its get. When it runs out, the task publishes reneged and its get is cancelled, so it takes nothing later. In the low-level API, cancel() on a put or get event that has not succeeded takes it out of its queue, as in SimPy: a cancelled get takes nothing, and a cancelled put adds nothing. item_field adds the item a YAML task's get took to its payload, and a builder function receives it as item:

    def collect(env, sampler, shop, key, area, task_id):
    """Takes the oldest parcel for its own area, or leaves after 20 seconds."""

    def publish(value):
        env.publish_event(key, value, task="collect", instance=task_id)

    flow = key.rsplit("-", 1)[0]
    env.stats.flow_started(flow)  # the courier enters the shop
    publish({"status": "queued"})
    env.stats.task_queued("collect", task_id)
    get = shop["parcels"].get(filter=lambda parcel: parcel["area"] == area)
    yield get | env.timeout(20)
    if not get.triggered:
        get.cancel()  # out of the queue, so it takes no parcel later
        publish({"status": "reneged"})
        env.stats.task_reneged("collect", task_id)
        env.stats.flow_ended(flow)
        return
    publish({"status": "started"})
    env.stats.task_started("collect", task_id)
    publish({"event_type": "parcel_collected", "parcel": get.value})
    env.stats.task_finished("collect", task_id)
    env.stats.flow_finished(flow)

    item.<field> can also be read in the task's put and next, after its get. Filtered Inventory uses a filter and patience on a shelf of shirts.

    Custom Store and Container Types

    A store or container of your own class changes how items or amounts go in and out. Subclass desflow.StoreBase (a simpy.Store) or desflow.ContainerBase (a simpy.Container) and override _do_put or _do_get, set PutQueue or GetQueue, or bind put and get to event classes of your own, as in SimPy. The constructor is SimPy's, (env, capacity=inf) for a store and (env, capacity=inf, init=0) for a container. Name the class with type: !python module.Class in a blueprint, type= in add_store and add_container, or type= in DynamicStore and DynamicContainer.

def build(env):
    """Builds the lane and the tank, in the builder's order."""
    return {
        # A lane of your own type; it holds two trucks
        "lane": DynamicStore(env, "Dock", "lane", type=Lane),
        # The tank holds 100, the capacity in the parameters
        "tank": DynamicContainer(env, "Dock", "tank"),

    The statistics and the conditions follow every change to a store's items or a container's level made by _do_put or _do_get, whether the override calls super() or not, and they are told once for each. ContainerBase compares the level before and after, so an override that returns True without changing the level reports nothing. A change to the length of put_queue or get_queue is reported to the conditions that read putters. or getters.; a queue class must support len() and remove(). A cancel() is reported from the event classes, so it works with a queue class of your own.

    A task's put stores its payload as the item, and its get passes the item on, unwrapped, whatever the type. A type cannot be given with priority: a type sets its own order, so subclass StoreBase and simpy.PriorityStore for a ranked store. A get with a filter needs a type that subclasses simpy.FilterStore, and a blueprint or run() that has none is refused with the task's name. A live capacity update reaches a type of your own as it does the default.

    Registry Paths, Readings and Conditions

    A container has three registry paths, <sim_id>.containers.<name>.current_cap, .max_cap and .level; a store has <sim_id>.stores.<name>.current_cap and .max_cap. With statistics at the minimal level or above, each publishes four readings, such as Shop.stats.containers.stock.level:

    Reading Store Container
    capacity items it can hold largest amount
    level items held amount held
    getters_waiting tasks waiting to get an item tasks waiting to take an amount
    putters_waiting tasks waiting to put an item tasks waiting to add an amount

    A condition can also read how many tasks wait at a store or container, and what a store holds:

    Name Reads
    putters.<name>, getters.<name> the number of puts or gets waiting, not counting one that is granted at once, as the putters_waiting and getters_waiting readings; len(put_queue) and len(get_queue) in the low-level API
    count(<store>) the number of items the store holds, as level.<store>
    count(<store>, <condition>) how many items meet the condition, which reads item.<field> of each
    items(<store>), items(<store>, item.<field>) the list of items, or that field of each; a priority store gives its items unwrapped

    in and not in read an items(...) list, as in payload.sku in items(shelf, item.sku), which is true while the shelf holds that sku. The store is a bare name, and count and items cannot be nested inside each other. The names are checked at load: each must be a store (putters. and getters. also a container).

    A condition that reads one of these names is checked again when a put or get joins or leaves a queue. A condition that does not, such as level.stock == 0, is checked as before. A queue change is not a change of level, so level_avg does not move. The marshal task of Example: Fuel Dock waits on putters.lane >= 1.

    def pack(env, sampler, shop, key, priority, task_id):
    """Queued, a packer by priority, a box from stock, packing, then a parcel."""
    path_id = "Shop.service.packing"

    def publish(value):
        env.publish_event(key, value, task="pack", instance=task_id)

    publish({"path_id": path_id, "status": "queued"})
    env.stats.task_queued("pack", task_id)  # counted as in progress
    with shop["packers"].request(priority=priority) as req:
        yield req
        # Waits while the stock is empty
        yield shop["stock"].get(1)
        publish({"path_id": path_id, "status": "started"})
        env.stats.task_started("pack", task_id)
        payload = {"event_type": "order_packed", "priority": priority}
        yield env.timeout(sampler.sample(env.registry.get_config(path_id)))
        # Waits while the store is full; wrap ranks the parcel by its priority
        yield shop["parcels"].put(shop["parcels"].wrap(payload, priority))
        publish(payload)
        env.stats.task_finished("pack", task_id)

    How It Works

    A container keeps a level between 0 and its capacity, with a queue of getters and a queue of putters. A get succeeds as soon as the level covers its amount, and a put as soon as there is room for all of it; until then each waits in its queue, in the order it arrived:

    A store keeps a list of items, up to its capacity. A put adds an item at the end, and a get takes the first, so items leave in the order they came; a get with a filter takes the first item its filter accepts:

    SimPy and desflow. Underneath are SimPy's Container; a FilterStore for a store, which serves its gets as Store does while no waiting get has a filter; and a PriorityStore for a priority store, which hands out the lowest item first. A full put that waits for room and an empty get that waits for an item or an amount are checked against plain SimPy in all three APIs; SimPy Compatibility lists the checks. SimPy's capacities are fixed when they are created; desflow's follow the registry, keep the registry's level in step with every put and get, and report each change to the statistics. SimPy and desflow compares the two.

    Under Live Changes

    • Capacity follows current_cap, clamped to between 0 and max_cap. A higher capacity wakes waiting putters. A capacity below what is held destroys nothing: puts wait until enough has been taken.
    • A container's level is set by an update to its level path, as a stock count or a restock from outside would. The new level is clamped to between 0 and current_cap, with a warning, and it wakes both queues: a higher level serves waiting getters, and a lower one can make room for putters.
    • A store or container with no limit can be given a number as current_cap during a run, and .inf or the text "inf" sets no limit again. Lowering destroys nothing, as above.
    • current_cap is the capacity, not a level. A model that used a container's current_cap as a level, such as the wear of a roll, moves it to level.

    Stability and Limits

    • A container that never refills blocks its getters for good, and a task that waits for stock while holding a resource blocks the resource too. Supply has to keep up with demand, as Stock shows.
    • Whole items. A store's capacity is a whole number or no limit, and it holds items, not amounts.
    • A put or get with wait: false is never cancelled, so a supply that outpaces its consumers grows the queue without end. A run drops what is still waiting when it ends.
    • A filter checks every waiting get on each put. A store with many waiting gets and a filter that rarely matches does work in proportion to both, as SimPy's FilterStore does.
    • One store or container per get or put. A task has at most one get and one put.
